# SVG Architecture Study - Phase 4: Style System & CSS Property Integration

## Overview

This document covers how SVG CSS properties are defined, computed, and used in Servo. Unlike HTML elements that use standard CSS properties defined in Servo's style system, SVG-specific properties like `fill`, `stroke`, `clip-path`, and `marker` come from the upstream **stylo** crate (Gecko's CSS engine). These properties flow through Servo's layout and display list systems but are largely **ineffective for inline SVGs** due to the serialization pipeline. Understanding how these properties work is critical for diagnosing the CSS inheritance breakage and for implementing proper SVG support.

## SVG CSS Property Architecture

### Source: Upstream Stylo Crate

Servo's CSS engine is `stylo` (Mozilla's Gecko style system), pulled as an external dependency. SVG-specific CSS properties are defined in the upstream `stylo` crate in property definition files (`.mako.py` templates, `properties.mako.rs`). These generate Rust structs accessed via `ComputedValues` methods.

### Access Pattern

```rust
// From any style reference:
style.get_svg()           // Returns &SVGStyle struct (stylo-generated)
style.get_svg().clip_path // Access individual property
```

### SVG Style Struct (`SVGStyle`)

Generated by `stylo`, this struct contains all SVG-specific CSS properties. Key properties include:

**Geometry Properties:**
- `clip_path: ClipPath` — CSS masking (`url()`, `path()`, shape values)
- `clip_rule: SVGClipRule` — `nonzero` / `evenodd` for clip paths

**Fill and Stroke:**
- `fill: SVGPaint` — fill paint (color, url, context-fill, none)
- `fill_opacity: Opacity` — fill opacity
- `fill_rule: SVGFillRule` — nonzero / evenodd
- `stroke: SVGPaint` — stroke paint
- `stroke_opacity: Opacity` — stroke opacity
- `stroke_width: SVGWidth` — stroke width
- `stroke_linecap: SVGStrokeLinecap` — butt, round, square
- `stroke_linejoin: SVGStrokeLinejoin` — miter, round, bevel
- `stroke_miterlimit: MiterLimit` — miter limit
- `stroke_dasharray: SVGDashArray` — dash pattern
- `stroke_dashoffset: SVGLength` — dash offset

**Marker Properties:**
- `marker_start: URLMarker` / `marker_mid: URLMarker` / `marker_end: URLMarker`

**Painting Properties:**
- `paint_order: SVGPaintOrder` — fill/stroke order
- `color_interpolation: SVGColorInterpolation`
- `color_interpolation_filters: SVGColorInterpolation`

**Text Properties:**
- `text_anchor: SVGTextAnchor` — start, middle, end
- `dominant_baseline: SVGDominantBaseline`
- `alignment_baseline: SVGAlignmentBaseline`

### Property Values

SVG CSS properties use special value types:

```rust
pub enum SVGPaint {
    None,
    Color(AbsoluteColor),
    ContextFill,    // #context-fill (marker inheritance)
    ContextStroke,  // #context-stroke
    PaintServer(Url), // url(#gradient)
}

pub enum ClipPath {
    None,
    Shape(Box<BasicShape>, ShapeGeometryBox),
    Box(ShapeGeometryBox),
    Url(Url),       // url(#clip-path-id)
}
```

## SVG CSS Properties Flow

### CSS Cascade for SVG Elements

```
1. Parse CSS rules (user-agent + author + inline styles)
2. Match selectors against SVG elements (svg namespace)
3. Cascade values from HTML ancestors through SVG subtree
   └── THIS IS WHERE INLINE SVG BREAKS:
       Serialization isolates SVG from HTML ancestors
4. Compute values (resolve percentages, inherit)
5. Apply to layout and rendering
```

**CSS Inheritance from HTML to SVG:**

In a proper implementation:
```html
<div style="fill: green">
    <svg>
        <text>Should be green</text>  <!-- inherits fill: green from div -->
    </svg>
</div>
```

With serialization:
```html
<div style="fill: green">
    <svg>
        <text>Black (default)</text>  <!-- data URL loaded as image → no CSS context -->
    </svg>
</div>
```

The serialization isolates the SVG's computed style. Even though `fill` is an inheritable SVG property that should flow from `<div>` through `<svg>` to `<text>`, the serialized data URL breaks this chain because it loads the SVG XML as an independent document.

### SVG Namespace Handling

SVG elements use the `ns!(svg)` namespace. CSS selectors can target them with:

```css
/* Namespace prefix */
@namespace svg url(http://www.w3.org/2000/svg);
svg|text { fill: red; }

/* Universal SVG selector */
*|* { }  /* matches all namespaces */
```

In Servo's selector matching, elements with `ns!(svg)` are treated as SVG elements. The `LayoutElement` trait provides `type_id()` which returns `LayoutNodeType` values like `SVGSVGElement`, `SVGImageElement`, or falls back to generic element matching.

## Key SVG CSS Properties in Layout

### clip-path: The Most Active SVG Property

The `clip-path` CSS property is the most actively used SVG-related property in Servo's layout code.

**Processing Chain:**

```
CSS Property → ComputedValues::get_svg().clip_path → StackingContext
    1. Style computation resolves `clip-path` value
    2. style_ext.rs checks if clip-path creates stacking context (line 770)
    3. clip.rs add_for_clip_path() processes ClipPath enum:
        - ClipPath::Shape → basic shapes (circle, ellipse, rect)
        - ClipPath::Box → geometry boxes (border-box, padding-box)
        - ClipPath::Url → SVG clipPath element reference
        - ClipPath::None → no clip
    4. WebRender clip chain ID is created if needed
```

**Stacking Context Creation** (style_ext.rs:770):
```rust
if self.get_svg().clip_path != ClipPath::None {
    return true;  // Creates stacking context
}
```

This means any element with `clip-path: url(#foo)` or `clip-path: circle()` creates a stacking context, matching the CSS masking spec.

**Clip Path Processing** (clip.rs:69-120):
```rust
pub(super) fn add_for_clip_path(
    &mut self,
    clip_path: ClipPath,
    parent_scroll_node_id: ScrollTreeNodeId,
    parent_clip_chain_id: ClipId,
    fragment_builder: BuilderForBoxFragment,
) -> Option<ClipId>
```

Processes `ClipPath` values:
1. Extracts geometry box from shape or box variant
2. Computes rect from fragment (margin, border, padding, content)
3. Creates clip for basic shapes or delegates to url resolution

**Url Clip Paths**: For `clip-path: url(#clip-path-id)`, the reference is to an SVG `<clipPath>` element. In Servo's current implementation, this URL resolution path has limited support since SVG elements are serialized rather than rendered as native DOM content.

### SVG Transforms

SVG elements can have CSS `transform` properties. The style system handles these through:

```rust
// style_ext.rs checks for effective transforms
style.has_effective_transform_or_perspective(FragmentFlags::empty())
```

**Transformable SVG Elements** (style_ext.rs:535-540):
> "...all SVG paint server elements, the clipPath element and SVG renderable elements with the exception of any descendant element of text content elements."

**Critical Issue for Crisp Transforms**: SVG `transform` is applied through CSS to the replaced element box. Since the SVG is already rasterized at natural size, CSS `transform: scale(4)` scales the bitmap. The original vector resolution is lost.

## SVG CSS Property Limitations in Servo

### Properties That Are Defined But Ineffective

These SVG CSS properties are defined in `stylo` and parsed by Servo's style system, but have **no rendering effect** because SVG is serialized:

| Property | Status | Reason |
|----------|--------|--------|
| `fill` | Parsed, not rendered | SVG rasterized by resvg with its own styles |
| `stroke` | Parsed, not rendered | Same as fill |
| `fill-opacity` | Parsed, not rendered | resvg handles its own opacity |
| `stroke-width` | Parsed, not rendered | Same as fill |
| `marker-*` | Parsed, not rendered | Same as fill |
| `paint-order` | Parsed, not rendered | Same as fill |
| `color-interpolation` | Parsed, not rendered | Same as fill |
| `text-anchor` | Parsed, not rendered | Same as fill |

### Properties That Have Partial Effect

| Property | Status | Effect |
|----------|--------|--------|
| `clip-path` | Partially works | Creates stacking context, basic shapes work on SVG container |
| `transform` | Partially works | Applied to SVG container box, but rasterized bitmap means blurry results |
| `opacity` | Works on container | Applied to SVG container as stacking context |
| `visibility` | Works on container | Standard CSS on the SVG replaced element |
| `overflow` | Works on container | Standard CSS on the SVG replaced element |

### Properties That Affect Rasterization

Some CSS properties influence **how** the SVG is rasterized:

1. **`image-rendering`**: Controls `tiny_skia` interpolation quality during WebRender display list creation (display_list/mod.rs:686)
2. **`transform`**: Applied to the SVG container box; affects the rectangle position/size for the rasterized image

## Style Extension Points

### style_ext.rs SVG-related Methods

**`is_replaced_content()`** (various locations):
- Returns `true` for SVG elements since they're treated as replaced elements

**`creates_stacking_context()`** (line 770):
- SVG `clip-path` unconditionally creates a stacking context
- SVG elements with `transform` create stacking contexts
- SVG elements with `opacity` create stacking contexts

**`transform_kind()`** (line 535):
- Identifies SVG transformable elements
- Includes svg namespace elements

### Display List Clip Integration

The clip processing in `clip.rs` handles SVG `clip-path`:

- **Basic shapes** (`circle()`, `ellipse()`, `inset()`, `polygon()`): Rendered through WebRender clip regions
- **Box references** (`border-box`, `padding-box`, etc.): Resolved to fragment geometry
- **Url references** (`url(#foo)`): Limited support for SVG clipPath element references

## Cascade Breakage Analysis

### Why CSS Inheritance Fails for Inline SVG

The serialization-based approach creates a fundamental CSS cascade boundary:

```
Normal HTML<->SVG inheritance:
    <div style="fill: green">         ← HTML ancestor
        <svg>                         ← SVG root (ns!svg)
            <use href="#shape" />     ← inherits fill
            <text>text</text>         ← inherits fill
        </svg>
    </div>

With serialization (current behavior):
    <div style="fill: green">         ← HTML ancestor
        <svg> ──serialize──► data:image/svg+xml;base64,...  ← considered replaced content
            └── All child elements lose parent context
    </div>
    (serialized SVG loaded as image: no CSS cascade from div)
```

**Root cause** at the style system level: When layout reaches the SVG element, it doesn't traverse SVG children as layout children. Instead, it treats the entire SVG as a replaced element (like `<img>`). The children's styles are never computed in the context of the parent document.

### Web Fonts at the Style Level

Web fonts require:
1. `@font-face` declarations in CSS
2. Font file loading from a URL
3. Font application to text elements via `font-family`

With serialization:
1. The SVG's `<style>` element may contain `@import` or `@font-face`
2. But these are serialized into the data URL
3. When loaded as an image, the data URL context doesn't trigger font loading
4. Even if loaded, fonts can't render in the rasterized bitmap from resvg without a shared font database

## Summary

The SVG style system infrastructure exists in Servo through the `stylo` crate, but it's largely ineffective for inline SVGs because:

1. **The serialization pipeline bypasses the CSS cascade** for SVG child elements
2. **SVG-specific properties** (`fill`, `stroke`, etc.) are parsed but never applied to rendering
3. **`clip-path`** is the only SVG CSS property that has meaningful layout impact
4. **Cascade boundaries** between HTML and SVG elements are broken by the serialization approach
5. **Web fonts** cannot work when SVG content is isolated from the document's font system

A proper implementation would need to integrate SVG elements directly into the CSS cascade, allowing properties like `fill`, `stroke`, and `font-family` to flow from HTML ancestors through SVG descendants without serialization boundaries.
